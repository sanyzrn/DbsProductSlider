## ۳. ترتیب اجرا و دلیل چینش

اصل چینش: **اول اعتبارسنجی آنچه ارسال شده، بعد رفع نقص همان، بعد قابلیت تازه، و آخر معماری بزرگ.** هر قابلیت جدید روی پایهٔ تأییدنشده ریسک را روی هم انباشته می‌کند.

### گام ۰ — دروازهٔ پذیرش ۲.۴.۰ (بدون کد، همین حالا)
- تأیید انتشار: تگ `v2.4.0`، دو ZIP و `SHA256SUMS` در Releases.
- اجرای V1 تا V4 روی سایت واقعی (نفس). نتیجهٔ منفی هر مورد، آن را به گام ۱ می‌آورد.
- **معیار عبور:** نصب/ارتقا بدون fatal؛ ذخیره و بازگشایی ویجت‌های قدیمی؛ سه منبع کار کنند.

### گام ۱ — نسخهٔ `2.4.1` (اصلاحات؛ کوچک و کم‌ریسک) — **انجام شد: N1، N2، R08، T10، N3، N4 و U11**

یادداشت R08: پدینگ قدیمی `.pce-v5-slider` از ۲.۳.۰ به بعد توسط `.pce-v5-wrapper .swiper{padding:0}` در CSS محلی Swiper بی‌اثر بود؛ فضای ایمنی اکنون با سلکتور هم‌وزن اعمال می‌شود و پیش‌فرض صفر است (صفحات موجود تغییر نمی‌کنند).

ترتیب داخلی:
1. **N1 + U11** — جداسازی استایل دکمهٔ دوم، چون نقص قابل مشاهدهٔ کاربر در قابلیتی است که تازه منتشر شد.
2. **N2** — کلمپ به سقف/کف مجاز با همان پیام راهنما.
3. **R08** — فضای امن hover برای کارت و grid.
4. **T10** — fallback تصویر خارجی.
5. **N3** — نمایش عنوان آیتم‌های انتخاب‌شده و حذف از پنل.
6. **N4** — پشتیبانی از مسیر مرورگر در متغیر محیطی برای اجرای محلی تست‌ها.
7. **V3** نتیجه اگر منفی بود: جایگزین مرتب‌سازی ووکامرس.

**معیار پذیرش:** تست رگرسیون برای هر مورد؛ `npm test` سبز؛ تغییر رنگ دکمهٔ اول دکمهٔ دوم را پر نکند.

### گام ۲ — دروازهٔ کیفیت پیش از «عمومی» (موازی با گام ۱ و ۳)
V5 تا V9 و E8. این گام کد محصول نمی‌افزاید اما برای ادعای عمومی لازم است. اگر هدف فعلی فقط سایت‌های شخصی است، می‌توان E1–E7 را عقب انداخت؛ V-ها را نه.

### گام ۳ — نسخهٔ `2.5.0` (فروشگاه)
ترتیب: **S2 → S1 → S5 → S3 → S4 → S6 → S7**.
- S2 و S1 کم‌ریسک‌اند و مستقیم روی query موجود می‌نشینند.
- S5 قبل از S3 می‌آید چون متن/رفتار دکمه ساختار داده‌ای S3 را ساده می‌کند.
- S4 دشوارترین است (تشخیص context)، پس بعد از آماده‌شدن بقیه.
- S6 باید پیش از اعلام «محصول همیشه به‌روز» تمام شود.

**شرط شروع:** گام ۰ پذیرفته شده و V3/V5 نتیجهٔ روشن دارند.

### گام ۴ — نسخهٔ `2.6.0` (ظاهر و کاتالوگ)
ترتیب: **U4 → U5 → U10 → U1 → U9 → U6 → U3 → U2 → U7 → U8**.
- U4/U5/U10/U1/U9 کوچک و مستقل‌اند و اثر مستقیم دارند.
- U6 تا U8 به CSS و کنترل‌های بیشتری وابسته‌اند؛ برای جلوگیری از شلوغی پنل (اکنون حدود صد کنترل سطح ویجت یا بیشتر)، هر کدام در بخش مناسب سازمان‌دهی شوند.

### گام ۵ — نسخهٔ `2.7.0` (انتقال داده)
**D1 → D2.** D1 ساده‌تر است و ارزش فوری دارد. D2 (CSV) فقط با سطح امنیتی کامل اضافه شود؛ پیش از شروع باید نیاز واقعی کاربران تأیید شود.

### گام ۶ — نسخهٔ `3.0` (معماری و سطوح اختیاری)
ترتیب اجباری: **A1 → A2 → A3 → A4**، سپس A5، و در نهایت A6/A7/A8 فقط با نیاز اثبات‌شده.
- A3 پیش‌نیاز A4 است؛ بدون renderer مستقل، شورت‌کد یعنی کپی‌کردن ویجت.
- A1 و A2 قبل از A3 می‌آیند تا بازنویسی روی ساختار تمیز انجام شود.
- A5 به فروشگاه واقعی وابسته است و باید از پوشهٔ تست Woo واقعی (E8) پشتیبانی شود.
- **همهٔ این مرحله باید شناسهٔ `pce_carousel_v5` و کلیدهای ذخیره‌شده را حفظ کند.**

### مسیر موازی انتشار عمومی
E1 → E2/E3 → E4 → E5 → E6. E1 باید قبل از هر انتشار عمومی و قبل از نام‌گذاری در مستندات انجام شود؛ دیر شدن آن هزینهٔ migration دارد.

| کاتالوگ داخلی (A8) | فقط اگر نیاز مدیریت محصول مشترک ثابت شود؛ هزینهٔ نگهداری بالاست |
| ادعای عددی دربارهٔ کندی/Lighthouse/نشت حافظه | تا اندازه‌گیری baseline (V8) ادعا نمی‌شود |
| تغییر پیش‌فرض صفحات قدیمی (مثل تراز یا contain) | فقط برای نصب‌های جدید یا با انتخاب صریح؛ صفحات موجود نباید تغییر کنند |

## ۷. یادداشت‌های اجرایی
- هر مورد باید با تست رگرسیون تکمیل شود؛ جایگزین‌های ایزوله وردپرس/Elementor/ووکامرس اثبات سازگاری نیستند.
- اتصال به ووکامرس و CPT باید بدون وابستگی اجباری باقی بماند؛ حالت دستی همیشه سالم کار کند.
- هر endpoint جدید: `capability` + `nonce` + اعتبارسنجی ورودی + سقف تعداد/اندازه.
- نام meta فیلد هرگز مجوز خواندن فیلد خصوصی یا محافظت‌شده نیست؛ allowlist الزامی است.
